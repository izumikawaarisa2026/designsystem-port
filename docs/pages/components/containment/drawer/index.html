コンポーネント / ドロワー/サイドナビSPEC No. 016

ドロワー/サイドナビ

画面の横にアプリの行き先の一覧を出すナビゲーション(スマートフォンで一時的に開くナビゲーションドロワーと、タブレット・PCで常に表示するサイドナビ)

コンポーネントイメージ(常時表示型の例)

画面の脇に、主要なナビゲーション項目を並べた領域。常時表示する形と、一時的に開閉するモーダル形の2系統がある。

目的・役割
行き先が多いアプリで、主な場所の一覧を見せて遷移できるようにする
よく使われる場面
スマートフォンアプリの≡メニュー(ドロワー)、メールアプリのフォルダ一覧や管理画面の左のメニュー(サイドナビ)
似たコンポーネント
主な場所が3〜5か所ならタブバー、補助の情報や操作を出すのはサイドシート

まず押さえる要点

  1. 1
    広い画面では隠さない
    サイドナビとして常に表示する
    Apple・NN group
  2. 2
    狭い画面では、行き先が4〜5個までならタブバー、それより多いときだけドロワーに入れる
    隠すナビゲーションは見つけにくいため
    AI解釈(見つけにくさはNN group)

意見が分かれる点

同じ問いに対して、系列によって答えが違う点。

主な行き先を、ボタンで開くメニュー(ドロワー)に隠してよい?
NN group
デスクトップでは隠さない。スマートフォンでも4個以下なら見せる。4個を超えて隠すなら、重要な情報へのページ内のリンクを添える
Google
狭い画面(コンパクト・中サイズ)では、行き先が5個以上か2階層を超えるときにモーダルのドロワーを使う。広い画面では常に表示するサイドナビ(ナビゲーションレール)にする。M3 Expressiveでは、ナビゲーションドロワーは推奨されず、広げると項目名まで並ぶナビゲーションレールに置き換える
Apple
iPhone向けの隠れたドロワーはない。まずタブバーを使い、収まらない領域はタブバーのサイドバーの形で見せる。サイドバーは隠せるようにするが、初期状態では隠さない
AI解釈: どの系列も「広い画面では隠さない」で一致する。分かれるのは狭い画面で、主な行き先が4〜5個までならタブバーで見せ、それより多いときだけドロワーに入れる、という順に考えると3系列とも両立する。
⚠ Googleの注意(M3 Expressive、2025年5月)

M3 Expressiveのアップデートで、ナビゲーションドロワーは推奨されなくなり、代わりに広げると項目名まで並ぶナビゲーションレール(expanded navigation rail)を使うとされている。このレールは、ドロワーとほぼ同じ働きを持ち、画面の広さの変化に合わせやすいとしている。下の比較表のGoogle欄にあるドロワーの決まりは、まだ更新していないアプリ向けの内容として読む。Apple・W3C・NN groupの内容には影響しない。

2つの種類と使用シーン

① ナビゲーションドロワー
主な画面スマートフォンなど狭い画面
見せ方ボタン(≡)を押して一時的に開く。後ろの画面を覆う(モーダル)
向いている場面行き先が多く、タブバー(3〜5か所)に収まらないとき

② サイドナビ(常に表示)
主な画面タブレット・PCなど広い画面

向いている場面広い画面で、主な行き先をいつも見せたいとき

四系列デザインシステム比較

AI解釈 ― 総括

広い画面ではサイドナビとして常に表示し、狭い画面で項目が多いときだけドロワーに隠す。隠したナビゲーションは見つけにくいからだ。NN groupは、隠すと見つけてもらえる割合がほぼ半分になり、作業時間がデスクトップで39%以上長くなると報告している。モバイルでも、トップの項目が4個以下なら見える形で出すよう勧める。

スマートフォンのドロワーは、Appleには該当する指針がない。GoogleにはModalのナビゲーションドロワーがある。ただしM3 Expressiveで非推奨にし、広げると項目名まで並ぶナビゲーションレールに置き換えるとしている。

広い画面では、主な行き先を常に見せる点で3系列が一致する(Appleのサイドバー、Googleのナビゲーションレール、NN groupの左の縦型ナビゲーション)。NN groupは、アイコンだけにせず文字のラベルを付けることも勧める。

W3Cにはドロワーという型がない。後ろを覆うものはダイアログ(モーダル)、常に見せるものはナビゲーションの領域として扱う。どちらも、複数のページで項目を同じ順に並べる(3.2.3)。

サイズ
該当なし
コンパクト・中サイズのブレークポイントではModal(またはタブバー/ナビゲーションレールへの置き換え)を使う。Webでは画面幅が320 CSS px未満なら、タブバーに置き換える。ドロワーの幅は360dp(Jetpack Composeのトークン)。
専用の数値基準はなく、一般のターゲットサイズの基準がかかる。2.5.8(レベルAA)は24×24 CSS px以上、2.5.5(レベルAAA)は44×44 CSS px(どちらも例外あり。詳しくは「ボタン」ページ)。
モバイルでは、項目が4個以下なら常に見せる。5個以上(4個を超える)ならやむを得ず隠すが、重要な情報へのページ内リンクも置く。
色
該当なし
色の値はデザイントークンで実装する。選択中の行き先は塗りのアイコン、未選択は枠線のアイコンで区別し、アクティブインジケーター(背景の図形)で今のページを示す。ドロワーの幅は360dp、インジケーターは高さ56dp・Secondary container・角丸Full、モーダルの容器はSurface container low・影Level 1(Jetpack ComposeのNavigationDrawerTokens)。

基本方針
該当なし
  • 大きなデバイスで画面を切り替えるコンポーネントで、目的の画面やアプリの機能(アカウントの切り替えなど)に届く。
  • 常に出すことも、メニューアイコンで開閉することもでき、いつも1つの行き先がアクティブ。
  • よく訪れる行き先を上に置き、関連する行き先はまとめる。
  • 主な行き先が5つ以上、階層が2段を超える、関係のない行き先の間を素早く遷移したい、大きな画面でナビゲーションレール/バーの代わりにしたい、といった場合に勧める。
  • タブバーなどほかの主なナビゲーションと併用せず、要件とブレークポイントに合わせて1つを選ぶ(コンパクト→タブバー、中/拡張→ナビゲーションレール、拡張/大/特大→Standardドロワー)。
  • アイコンはすべての行き先に付けるか、どれにも付けないかにそろえる。
  • 後ろの操作を完全に遮るモーダルなドロワーには、WAI-ARIAのDialog(Modal)パターンが合う。
  • ダイアログであることを伝え、Tab/Shift+Tabでドロワーの外にフォーカスが出ないようにし(フォーカストラップ)、Escキーで閉じられ、名前を付け、見える閉じるボタンを持つ。
  • モーダルと伝えるのは、後ろの操作を完全に遮り、見た目でも覆っている場合だけ。
  • 中身が複数のページで共通のナビゲーションなら、3.2.3(レベルAA)により、どのページで開いても項目を同じ順番で並べる(利用者が並びを変えた場合を除く)。
  • 調査では、メインナビゲーションを隠すと内容の見つけやすさがほぼ半分に下がり、作業時間はデスクトップで39%以上、モバイルで15%長くなった。
  • 隠れたナビゲーションは、常に見せる・併用する形より21%難しく感じられ、使われる割合も低い(デスクトップで27%、常に見せる/併用は48〜50%)。
  • 原因は、アイコンが目立たない・中身が予測できない・開く手間・実装がそろっていない・パターンに慣れていない、の5つ。
  • デスクトップでは、ハンバーガーアイコンのような隠れたナビゲーションを使わず、主な選択肢をいつも見せる。

該当なし

アクセシビリティ(WCAG基準)
該当なし
操作可能(Operable) ― 項目のアクセシビリティラベルは通常、行き先の名前と同じで、ラベルが正しく結び付いていれば支援技術はラベルに続けて役割を読み上げる。Android Views(MDC-Android)は、詳しいラベルの設定や役割の読み上げに対応していない。表示が曖昧なら(例:「最近使用した項目」)、アクセシビリティラベルに補足を加える。
堅牢(Robust)・操作可能(Operable) ― フォーカスの閉じ込め・Escで閉じる・ラベル付け(4.1.2、2.1.1)。3.2.3は「理解可能(Understandable)」の予測可能(3.2)。
根拠となる原則 ― 適合区分ではなく、利用のデータ(見つけやすさ・作業時間・満足度)にもとづく調査の結果。
ユースケース
  • 該当なし
  • 主な行き先が5つ以上、または階層が2段を超える製品で使う
  • コンパクト/中サイズはModal、拡張/大/特大はStandardを使う(ほかのナビゲーションと併用しない)
  • アイコンを使うならすべての行き先に付ける(一部だけにしない)
  • モーダル(後ろを遮る)ドロワーにはDialog(Modal)パターンを使う
  • 後ろを完全に遮り、見た目でも覆う場合だけ、モーダルと伝える
  • どのページで開いても、ドロワーの項目を同じ順番に並べる(3.2.3)
  • デスクトップでは隠れたナビゲーションを避け、主な選択肢をいつも見せる
  • モバイルで項目が4個以下なら見える形にする
  • モバイルで4個を超えて隠すなら、重要な情報へのページ内リンクも置く

メモ
該当なし

Standard / Modal(ドロワー): Standardは拡張/大/特大のブレークポイント向けの、常に出す(または開閉できる)ドロワー。Modalはコンパクト/中サイズ向けで、スクリムで後ろの内容の操作を遮り、レイアウトグリッドに影響しない一時的なドロワー。

アクティブインジケーター: 今のページを示す背景の図形。選択した行き先は塗りのアイコン、未選択は枠線のアイコンで区別する。

3.2.3 Consistent Navigation・レベルAA: 複数のページで繰り返し出るナビゲーションを、いつも同じ順番で並べること。利用者が自分で並びを変えた場合は除く。

基本方針
  • サイドバーは、アプリの主な領域への遷移に使う。
  • 縦にも横にも広い場所が要るため、場所が限られるならタブバーのほうがよい。
  • 多くのアプリでは、タブバーとサイドバーを切り替えられる形のタブバーを使えば、どちらかを選ぶ必要はない。
  • iOS・iPadOSでは、まずタブバーを検討し、収まらない領域はタブバーのサイドバーの形で見せる。
  • 階層は2段までにし、それより深いときはスプリットビューで一覧を挟む。
  • 項目は利用者が並べ替えられるようにする。
  • 利用者がサイドバーを隠せるようにする(iPadOSは画面の端からのスワイプ、macOSは表示メニューなど)。ただし見つけてもらえるよう、初期状態では隠さない。
  • iPhone向けの隠れたドロワーのコンポーネントはない。
  • 中くらいの画面で画面を切り替えるコンポーネント。
  • M3 Expressiveで、広げると項目名まで並ぶようになり、その形がナビゲーションドロワーの代わりとされた。
  • 広げた形は非モーダルで、アイコンだけの形に戻せる。
  • M3の本文では、中・拡張のブレークポイントではナビゲーションレール、拡張・大・特大ではStandard(常時表示)のドロワーを使うとしている。
  • ナビゲーションドロワーは、タブバーなどほかの主なナビゲーションと併用しない。
  • Appleのサイドバーのような、常に表示するモーダルではないナビゲーションは、ダイアログではなく、ナビゲーションの領域として扱うのが合う(AI解釈)。
  • 複数のページで共通のナビゲーションなら、3.2.3(レベルAA)により、どのページでも項目を同じ順番で並べる。
  • 縦型のナビゲーションは、多くのカテゴリを収められ、項目が増えても対応しやすい。
  • 縦のリストは横並びより目で探しやすく、モバイルにも移しやすい。一方で横型より場所を取り、内容に使える面積が減る。
  • 左側に置き、目立つデザインにする。
  • 縦と横に同じメニューを重ねて置かない。
  • アイコンだけにして文字を隠さない。
  • 長いメニューでは、重要でない項目を下に置く。
