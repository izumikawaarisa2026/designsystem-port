コンポーネント / エラー表示SPEC No. 023

エラー表示

入力の間違いを見つけたときに、何が問題でどう直せばよいかを伝える表示

まず押さえる要点

  1. 1
    色だけで伝えない
    枠の色に加えて、アイコンと文で伝える
    Apple・Google・W3C
  2. 2
    何が問題かを書く
    W3C 3.3.1
  3. 3
    どう直せばよいかを書く
    W3C 3.3.3・NN group
  4. 4
    利用者を責めず、入力した内容は残す
    NN group
  5. 5
    重要な操作は、事前に防ぐ
    W3C 3.3.4
コンポーネントイメージ(共通形状)
meail@example
⚠メールアドレスの形式が正しくありません

エラー状態の枠線に加え、アイコン・テキストで問題と訂正方法を伝える。色だけに頼らない表示が各系列で共通して求められている。

目的・役割
間違いの場所と理由、直し方を伝え、入力をやり直せるようにする
よく使われる場面
フォームの入力欄の下のエラー文、送信後のエラーのまとめ
似たコンポーネントとの違い
いつ検証するか(入力中・欄を離れたとき・送信時)はバリデーション

良い例・悪い例 ― エラーの伝え方

◯ 良い例
メールアドレス
taro.example.com
!「@」が入っていません。例: name@example.com

赤い枠に加えて、エラーのアイコンと、欄の近くに「何が問題で、どう直すか」の文がある。入力した内容も残っている。

✕ 悪い例(1)
メールアドレス
taro.example.com

枠が赤くなるだけで、アイコンも文もない。色だけで伝えている。

✕ 悪い例(2)
メールアドレス
taro.example.com
!入力エラーです

文はあるが「入力エラーです」だけで、何が問題でどう直せばよいか分からない。

根拠: W3C 3.3.1(エラーの特定・A)・3.3.3(エラーの修正提案・AA)・1.4.1(色だけで伝えない)、Apple・Google(アイコンと文を併用)、NN group(利用者を責めず、具体的な直し方を示し、入力を残す)。

図は概念図。

AI解釈 ― 総括

このコンポーネントで最も体系的なのはW3Cだ。「エラーの特定(3.3.1・レベルA)」→「エラーの修正提案(3.3.3・レベルAA)」→「誤り防止(法的・金融・データ)(3.3.4・レベルAA)」という3段階の達成基準が積み上がっており、単に「エラーを表示する」だけでなく「何が間違っているか」「どう直せばよいか」「重要な操作では事前に防ぐ」という段階的な要求になっている。

Nielsen Norman Groupのガイドラインは、この3段階の要求と方向性が一致する実務的な文章表現の指針を提供している。「ユーザーを責めない」「具体的な解決策を示す」「入力を保持する」といった原則は、W3Cの「エラーの修正提案」(3.3.3)を実際にどう書くかという具体化と言える。

興味深いのは、Apple・Googleどちらにも、エラー表示やバリデーションという独立したコンポーネント名は見当たらないことだ。両社とも、これをテキストフィールドという個別コンポーネントの「状態の1つ」として扱っており、W3C・NN groupのような横断的な原則としての独立したページはない。

Apple・Google・W3C・NN groupの4系列が一致しているのは、「色だけに頼ってはならない」という原則だ。Apple(アイコン・テキストの併用)・Google(エラーアイコンを色に加わる2つ目の手がかりとして強く勧める)・W3C(1.4.1の色の用途+テキストによる説明の必須化。枠線やアイコンのコントラストは1.4.11)・NN group(太字・高コントラストなど複数の手がかりを重ねる)がそれぞれ独立に同じ結論に達している点は、実装上の優先度が高い指摘だと言える。

色
エラー専用の色の規定はない。全体の方針として、色だけに頼らず、形やアイコンなどの手がかりを足すよう求めている(HIG Accessibility)。
エラー状態では、枠線・ラベル・エラーテキストにエラーの色を使う。あわせてエラーアイコンを表示することを強く勧めている。視覚に障害のある人にとって、色に加わる2つ目の手がかりになるため。
1.4.1(色の用途・レベルA)により、エラーを色の違いだけで伝えてはいけない(アイコンや文字も添える)。1.4.11(非テキストのコントラスト)は役割が別で、エラーを示す枠線やアイコンなどの視覚的要素に3:1以上のコントラスト比を求める。エラーは視覚的表示だけでなく、必ずテキストで説明する必要がある(3.3.1)。
色だけに頼らず、太字・高コントラストの赤色文字など複数の視覚的手がかりを重ねて使うべきとしている。
基本方針
AppleのHIGには、エラー表示の専用ページはない。入力の決まり(Entering data)で、値は入力されたらすぐに確かめ、問題があればすぐに知らせて、その場で直せるようにするとしている。表示のタイミングの比較は「バリデーション」ページで扱う。
Material Design 3にはエラー表示という独立したコンポーネントはなく、テキストフィールドの状態の1つとして「エラー状態」を持つ。検証する欄では、欄の下のサポートテキストをエラーテキストに入れ替える(行が増えてレイアウトが動かないようにするため)。エラーが1種類ならその避け方を、複数ありうるなら最も起きやすいエラーの避け方を書く。
3.3.1は、入力エラーが自動検出された場合、エラーのある項目を特定し、エラーの内容をテキストで説明することを求める(レベルA)。必須項目の未入力にはaria-invalid等での特定、書式が不正な入力にはARIAのアラートやライブリージョンでの説明が代表的な実装手法とされている。3.3.3はこれを一段進め、訂正方法が分かっている場合はその訂正案自体を提示することを求める(レベルAA、例: 月の名前を入れる欄に「12」と入力されたら、月名の一覧を示すか、「12月(December)のことですか?」と提案する)。3.3.4は、法的・金融的な確約やデータの変更・削除、試験の回答の送信を伴う場面において、取消可能・入力エラーの検査と訂正機会・送信前の確認という3つの手段のいずれかを備えることを求める(レベルAA)。
エラーはフィールドの近くに表示し、認知的な負荷を減らすべきとしている。理想的には全ての検証をインラインで行い、ユーザーが1つのフィールドの入力を終えた直後に、その場でエラーの有無を示すべきとしている。これによりユーザーは入力の途中で修正でき、やり直しのコストを減らせるとしている。エラーメッセージは平易な言葉で、簡潔かつ正確に問題を説明し、具体的な解決策を提示すべきで、ユーザーを責める表現(「無効」「不正」など)は避けるべきとしている。
例外・許容ケース
エラーは問題の起きた場所のできるだけ近くに出し、相手を責めず、直し方が分かる文言にする。「パスワードが短すぎます」より「8文字以上のパスワードを選んでください」のほうが役に立つ、としている(HIG Writing)。
エラーテキストが長い場合は複数行に折り返してよいが、そのぶん欄どうしの間隔を十分にとり、レイアウトを押し出さないようにする。
3.3.3のエラーの修正提案は、それによってセキュリティや機能の目的が損なわれる場合(パスワード入力欄など)は除外されるとしている。3.3.4は全てのページに適用されるわけではなく、法的確約・金融取引・データの変更や削除・試験の回答送信を伴うページに限定される。
ユーザーが実際に何らかの入力を行うまでは、エラーを早まって表示すべきではないとしている。前の入力内容は保持し、ユーザーがゼロから入力し直す必要がないようにすべきとしている。可能であれば、正しい候補を推測し、小さな一覧からユーザーが選べるようにするとよいとしている。ユーモアは繰り返されると陳腐化するため避けるべきとしている。また、「知っておくとよい」程度の軽微な問題には、条件付きのラベル・トースト・バナーなど操作の少ない表示を使い、作業の妨げになる問題にはモーダルダイアログで対応を求める、と使い分けている。入力欄のエラーは、欄の近くに消えない形で出すのが基本だ(トーストは自動で消え、読み逃しやすいため。AI解釈)。
アクセシビリティ(WCAG基準)
記載なし。一般的な原則として、色だけに頼らない状態表示が挙げられている。
操作可能(Operable)・知覚可能(Perceivable) ― エラーは色だけでなく、エラーテキストとエラーアイコンでも伝える(エラーアイコンは色に加わる2つ目の手がかりとして強く勧めている)。
理解可能(Understandable) ― 3.3.1・3.3.3・3.3.4はガイドライン3.3「入力支援」の基準で、POUR原則のうち「理解可能」に属する。補助として、色だけに頼らないこと(1.4.1)とエラー表示のコントラスト(1.4.11)は「知覚可能」に属する。認知障害・視覚障害・運動障害のあるユーザーが、エラーによってフォームの送信を断念せずに済むようにするという意図が明記されている。
根拠となる原則 ― POURのような適合区分ではなく、エラーメッセージの伝わりやすさ・修正のしやすさに基づく実務的な指針。
ユースケース
  • 問題を知らせて、すぐに訂正できるようにする(表示のタイミングは「バリデーション」ページを参照)
  • エラーメッセージは次にすべき行動を説明する(エラーコードや汎用文言は避ける)
  • 色だけでなくアイコン・テキストラベルも併用して状態を伝える
  • 無効な入力にはエラーカラーの枠線・ラベル・サポートテキストを適用する
  • エラーであることを示す末尾アイコンを併用する
  • エラーテキストで具体的な訂正方法を伝える
  • エラーは項目の特定+テキストによる説明の両方を必ず行う(視覚表示だけにしない)
  • 訂正方法が分かっている場合は具体的な訂正案を提示する(セキュリティ上避けるべき場合を除く)
  • 法的・金融・データ変更・試験送信を伴う場面では、取消可能/訂正機会/送信前確認のいずれかを用意する
  • フィールドの近くにインラインでエラーを表示し、入力直後に検証する
  • エラーメッセージは平易な言葉で具体的な解決策を示し、ユーザーを責めない
  • 軽微な問題(知っておくとよい情報)にはインライン表示・トースト・バナーを、作業を止める深刻な問題にはモーダルダイアログを使い分ける。ただし入力欄のエラーは、欄の近くに消えない形で出す(トーストは自動で消え、読み逃しやすい)

3.3.1 Error Identification(レベルA): 入力エラーが自動検出された場合、エラーの項目を特定し、エラーの内容をテキストでユーザーに説明しなければならないという基準。視覚的な表示だけでは不十分とされる。

3.3.3 Error Suggestion(レベルAA): 入力エラーが自動検出され、訂正方法が分かっている場合、セキュリティや目的を損なわない限り、その訂正案をユーザーに提示しなければならないという基準。

3.3.4 Error Prevention(レベルAA): 法的・金融的な確約、ユーザーデータの変更・削除、試験の回答の送信を伴うページでは、「取消可能」「入力エラーを検査して訂正機会を与える」「送信前に確認・訂正できる仕組みがある」のいずれかを満たさなければならないという基準。
