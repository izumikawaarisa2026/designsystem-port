コンポーネント / エラー表示SPEC No. 023

エラー表示

入力の間違いを見つけたときに、何が問題でどう直せばよいかを伝える表示

コンポーネントイメージ(共通形状)
meail@example
⚠メールアドレスの形式が正しくありません

エラー状態の枠線に加え、アイコン・テキストで問題と訂正方法を伝える。色だけに頼らない表示が各系列で共通して求められている。

目的・役割
間違いの場所と理由、直し方を伝え、入力をやり直せるようにする
よく使われる場面
フォームの入力欄の下のエラー文、送信後のエラーのまとめ
似たコンポーネント
いつ検証するか(入力中・欄を離れたとき・送信時)はバリデーション

まず押さえる要点

  1. 1
    色だけで伝えない
    枠の色に加えて、アイコンと文で伝える
    Apple・Google・W3C
  2. 2
    何が問題かを書く
    W3C 3.3.1
  3. 3
    どう直せばよいかを書く
    W3C 3.3.3・NN group
  4. 4
    利用者を責めず、入力した内容は残す
    NN group
  5. 5
    重要な操作は、事前に防ぐ
    W3C 3.3.4

良い例・悪い例 ― エラーの伝え方

◯ 良い例
メールアドレス
taro.example.com
!「@」が入っていません。例: name@example.com

赤い枠に加えて、エラーのアイコンと、欄の近くに「何が問題で、どう直すか」の文がある。入力した内容も残っている。

✕ 悪い例(1)
メールアドレス
taro.example.com

枠が赤くなるだけで、アイコンも文もない。色だけで伝えている。

✕ 悪い例(2)
メールアドレス
taro.example.com
!入力エラーです

文はあるが「入力エラーです」だけで、何が問題でどう直せばよいか分からない。

根拠: W3C 3.3.1(エラーの特定・A)・3.3.3(エラーの修正提案・AA)・1.4.1(色だけで伝えない)、Apple・Google(アイコンと文を併用)、NN group(利用者を責めず、具体的な直し方を示し、入力を残す)。

図は概念図。

AI解釈 ― 総括

このコンポーネントで最も体系的なのはW3Cだ。「エラーの特定(3.3.1・レベルA)」→「エラーの修正提案(3.3.3・レベルAA)」→「誤り防止(法的・金融・データ)(3.3.4・レベルAA)」という3段階の達成基準が積み上がっており、単に「エラーを表示する」だけでなく「何が間違っているか」「どう直せばよいか」「重要な操作では事前に防ぐ」という段階的な要求になっている。

Nielsen Norman Groupのガイドラインは、この3段階の要求と方向性が一致する実務的な文章表現の指針を提供している。「ユーザーを責めない」「具体的な解決策を示す」「入力を保持する」といった原則は、W3Cの「エラーの修正提案」(3.3.3)を実際にどう書くかという具体化と言える。

興味深いのは、Apple・Googleどちらにも、エラー表示やバリデーションという独立したコンポーネント名は見当たらないことだ。両社とも、これをテキストフィールドという個別コンポーネントの「状態の1つ」として扱っており、W3C・NN groupのような横断的な原則としての独立したページはない。

Apple・Google・W3C・NN groupの4系列が一致しているのは、「色だけに頼ってはならない」という原則だ。Apple(アイコン・テキストの併用)・Google(エラーアイコンを色に加わる2つ目の手がかりとして強く勧める)・W3C(1.4.1の色の用途+テキストによる説明の必須化。枠線やアイコンのコントラストは1.4.11)・NN group(太字・高コントラストなど複数の手がかりを重ねる)がそれぞれ独立に同じ結論に達している点は、実装上の優先度が高い指摘だと言える。

エラー専用の色の規定はない。全体の方針として、色だけに頼らず、形やアイコンなどの手がかりを足す(HIG Accessibility)。
エラー状態では、枠線・ラベル・エラーテキストにエラーの色を使う。エラーアイコンも出すことを強く勧める(視覚に障害のある人にとって、色に加わる2つ目の手がかりになるため)。
1.4.1(色の用途・レベルA)により、エラーを色の違いだけで伝えない(アイコンや文字も添える)。1.4.11(非テキストのコントラスト)は別の役割で、エラーを示す枠線やアイコンに3:1以上を求める。エラーは見た目だけでなく、必ず文字で説明する(3.3.1)。
色だけに頼らず、太字・コントラストの高い赤い文字など、複数の手がかりを重ねる。
基本方針
エラー表示の専用ページはない。Entering dataで、値は入力されたらすぐ確かめ、問題があればすぐ知らせて、その場で直せるようにするとする。表示のタイミングは「バリデーション」ページで比べる。
エラー表示のコンポーネントはなく、テキストフィールドの状態の1つとして「エラー状態」を持つ。検証する欄では、欄の下のサポートテキストをエラーテキストに入れ替える(行が増えてレイアウトが動かないようにするため)。エラーが1種類ならその避け方を、複数ありうるなら最も起きやすいエラーの避け方を書く。
3.3.1は、入力エラーを自動で見つけたら、エラーのある項目を特定し、エラーの内容をテキストで説明することを求める(レベルA)。代表的な実装は、必須項目の未入力ならaria-invalidなどで特定、書式の誤りならARIAのアラートやライブリージョンで説明。3.3.3はさらに、直し方が分かっていれば訂正案を示す(レベルAA。例: 月の名前の欄に「12」と入れたら、月名の一覧を示すか「12月(December)のことですか?」と提案する)。3.3.4は、法的・金融的な確約やデータの変更・削除、試験の回答の送信を伴う場面で、取り消せる・検査して直す機会を与える・送信前に確認する、のどれかを備える(レベルAA)。
エラーは欄の近くに出し、認知の負担を減らす。理想はすべての検証をインラインで行い、1つの欄を入力し終えた直後にその場でエラーの有無を示すこと。入力の途中で直せ、やり直しの手間が減る。エラーメッセージは平易な言葉で、短く正確に問題を説明し、具体的な解決策を示す。利用者を責める表現(「無効」「不正」など)は避ける。
例外・許容ケース
エラーは問題の場所のできるだけ近くに出し、相手を責めず、直し方が分かる文言にする。「パスワードが短すぎます」より「8文字以上のパスワードを選んでください」のほうが役に立つ(HIG Writing)。
エラーテキストが長ければ複数行に折り返してよいが、欄どうしの間隔を十分にとり、レイアウトを押し出さない。
3.3.3は、セキュリティや目的を損なう場合(パスワードの欄など)は除外。3.3.4は、法的確約・金融取引・データの変更や削除・試験の回答の送信を伴うページだけにかかる。
実際に入力するまでは、エラーを早まって出さない。前の入力は残し、ゼロから入れ直させない。できれば正しい候補を推測し、小さな一覧から選べるようにする。ユーモアは繰り返すと陳腐になるため避ける。「知っておくとよい」程度の軽い問題には条件付きのラベル・トースト・バナーなど操作の少ない表示を、作業を妨げる問題にはモーダルダイアログを使う。入力欄のエラーは、欄の近くに消えない形で出すのが基本(トーストは自動で消え、読み逃しやすいため。AI解釈)。
アクセシビリティ(WCAG基準)
記載なし。一般の原則として、色だけに頼らずに状態を示す。
操作可能(Operable)・知覚可能(Perceivable) ― エラーは色だけでなく、エラーテキストとエラーアイコンでも伝える(アイコンは色に加わる2つ目の手がかりとして強く勧める)。
理解可能(Understandable) ― 3.3.1・3.3.3・3.3.4は「入力支援」(3.3)の基準。色だけに頼らないこと(1.4.1)とエラー表示のコントラスト(1.4.11)は「知覚可能」。認知・視覚・運動に障害のある人が、エラーでフォームの送信をあきらめずに済むようにする、という意図。
根拠となる原則 ― 適合区分ではなく、エラーメッセージの伝わりやすさと直しやすさにもとづく実務の指針。
ユースケース
  • 問題を知らせて、すぐに訂正できるようにする(表示のタイミングは「バリデーション」ページを参照)
  • エラーメッセージは次にすることを説明する(エラーコードや決まり文句は避ける)
  • 色だけでなくアイコンや文字でも状態を伝える
  • 無効な入力では、枠線・ラベル・サポートテキストをエラーの色にする
  • エラーを示す末尾のアイコンも出す
  • エラーテキストで具体的な訂正方法を伝える
  • エラーは項目の特定と文字での説明を必ず両方行う(見た目だけにしない)
  • 直し方が分かっていれば具体的な訂正案を示す(セキュリティ上避けるべき場合を除く)
  • 法的・金融・データの変更・試験の送信を伴う場面では、取り消し/直す機会/送信前の確認のどれかを用意する
  • 欄の近くにインラインでエラーを出し、入力の直後に検証する
  • エラーメッセージは平易な言葉で具体的な解決策を示し、利用者を責めない
  • 軽い問題(知っておくとよい情報)にはインライン表示・トースト・バナーを、作業を止める深刻な問題にはモーダルダイアログを使う。ただし入力欄のエラーは、欄の近くに消えない形で出す(トーストは自動で消え、読み逃しやすい)

サイズ: 専用の数値基準はない。エラーを直すためのUI要素にも、一般のターゲットサイズの基準(WCAG 2.5.8/2.5.5。どちらも例外あり)がかかる。

3.3.1 Error Identification(レベルA): 入力エラーを自動で見つけたら、その項目を特定し、エラーの内容を文字で説明すること。見た目の表示だけでは足りない。

3.3.3 Error Suggestion(レベルAA): 入力エラーを自動で見つけ、直し方が分かっているなら、セキュリティや目的を損なわない限り、訂正案を示すこと。

3.3.4 Error Prevention(レベルAA): 法的・金融的な確約、データの変更・削除、試験の回答の送信を伴うページでは、「取り消せる」「入力エラーを検査して直す機会を与える」「送信前に確認・訂正できる」のどれかを満たすこと。
