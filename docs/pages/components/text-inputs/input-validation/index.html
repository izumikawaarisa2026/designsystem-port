コンポーネント / バリデーションSPEC No. 040

バリデーション

入力が正しいかを、いつ確かめるか(入力中・欄を離れたとき・送信時)の考え方だ。

検証タイミングの3つの選択肢
入力中
多くの場合は検証しない
フィールドを離れた時
既定のタイミング(NN group・Appleはメールアドレスなど)
送信時
必須項目の見落としを検知

NN groupは欄を離れたときの検証を既定とし、Appleもメールアドレスなどは別の欄に移ったときに確かめるとしている。入力中に示すのは、パスワードの条件の一覧(NN group)や、ユーザー名・パスワードの作成(Apple)など、決まった場面に限られる。

目的・役割
間違いを早めに知らせつつ、入力の途中で邪魔をしないタイミングを選ぶ
よく使われる場面
メールアドレス・パスワードの確認、会員登録・購入のフォーム
似た部品との違い
見つけたエラーの見せ方はエラー表示

意見が分かれる点

5つのタイミングの解説

それぞれのタイミングで何をするのか、メールアドレス欄を例にした画面イメージ(概念図)と、良い点・注意点を並べた。

① 入力前 ― 書式のヒントを先に示す
メールアドレス
name@example.com

何をするかエラーが起きる前から、入力の形式や条件を欄の下などに表示しておく。厳密には検証ではなく、エラーを未然に防ぐための準備。
良い点そもそも間違いが起きにくくなる。エラー時に同じ場所の文を差し替えれば、レイアウトも動かない。
注意点欄の中のプレースホルダーだけに書くと、入力を始めた時点で消えてしまう(NN groupが別の記事で指摘)。

② 入力中 ― リアルタイム検証

✕ 形式が正しくありません(まだ入力の途中なのに表示されてしまう例)

四系列デザインシステム比較

AI解釈 ― 総括

検証タイミングについて最も具体的な指針を持つのはNielsen Norman Groupだ。「入力中(タイピング中)にエラーを出さない」「フィールドを離れた時点で検証する」を原則としつつ、パスワードの要件チェックリストのような場面に限りリアルタイム検証を認めるという、原則+例外の形で整理されている。

Appleは「入力されたらすぐに確かめ、問題があればすぐに知らせる」(Entering data)としたうえで、メールアドレスは別の欄に移ったとき、ユーザー名・パスワードの作成は別の欄に移る前に確かめる(Text fields)と、内容でタイミングを分けている。いつ検証するかは系列で分かれる(上の「意見が分かれる点」)。

W3C(WCAG)は、「いつ検証すべきか」を定めていない。ARIA19はエラーを動的に知らせる仕組み(ライブリージョン)を、G199は送信が成功したことの知らせ方を扱うが、どちらも検証のタイミングではない。WCAGは「エラーをどう伝えるか」(「エラー表示」ページで扱う3.3.1・3.3.3・3.3.4)には具体的で、「いつ」には中立だ。

Googleは「サポートテキストをエラーテキストに入れ替える」という見せ方を定めているが、いつ検証するかはM3のページに書かれていない。エラーの前から書式のヒントをサポートテキストで示しておく点は、NN groupの「入力途中で急がせない」という考え方と相性のよい作りだ。

位置づけ
値は入力されたらすぐに確かめ、問題があればすぐに知らせる(動的な検証)。タイミングは内容で変え、メールアドレスは別の欄に移ったとき、ユーザー名・パスワードの作成は別の欄に移る前に確かめる
検証する欄では、欄の下のサポートテキスト(書式のヒント)を、同じ位置のエラーテキストに入れ替える(レイアウトを動かさないため)。いつ検証するかの決まりは記載なし
検証を「いつ行うべきか」の規範的な基準は見当たらない。ARIA19はエラーを動的に通知する技術的な仕組み(ライブリージョン)を示すが、タイミング自体は実装者の判断に委ねている。G199は送信成功時のフィードバック提供を推奨する、数少ない「タイミング」に触れた技術
検証タイミングについて最も具体的な実務指針を持つ。原則は「フィールドを離れた時」に検証し、入力中(タイピング中)にエラーを出すことは避けるべきとしている。パスワードの要件チェックリストのような特殊なケースでのみ、入力中のリアルタイム検証を許容する
基本方針
長いフォームを書き終えてから戻って直すのは利用者の負担になるため、値は入力されたらすぐに確かめ、問題を見つけたらすぐに知らせて、その場で直せるようにするとしている(Entering data)。どの時点で確かめるかは内容によるとし、メールアドレスは別の欄に移ったときに確かめ、ユーザー名・パスワードの作成は別の欄に移る前に確かめるとしている(Text fields)。
Material Design 3のテキストフィールドは、通常は欄の下の「サポートテキスト」で使い方や書式のヒントを示し、パスワードのように検証する欄では、エラーのときにサポートテキストをエラーテキストに入れ替える。行が増えてレイアウトが動くのを避けるためとしている。
WAI「Validating Input」チュートリアルは、クライアント側での検証は一般に良いユーザー体験につながり、エラーの解決を分かりやすくするとされているが、検証を「いつ」実行すべきか(リアルタイム/フォーカス離脱時/送信時)を指定する記述はない。可能な限り、ユーザーが入力内容を確認し訂正できる機会を持てるようにすべきだ、という一般原則にとどまる。ARIA19(role="alert"またはライブリージョンでエラーを識別する技術)は、エラーメッセージをライブリージョンに動的に挿入してスクリーンリーダーに通知する仕組みは規定しているが、いつ挿入するかというタイミング自体は実装者の判断に委ねられており、技術の例では送信時に検証し500ミリ秒待ってから挿入する例が示されているのみ。G199(送信成功時のフィードバック提供)は、送信が成功したことを明示的に伝えるフィードバックを提供すべきだとされており、検証タイミングというより送信「後」の結果通知に関する技術。WCAG 2.2で追加された3.3.7(レベルA)は、同じ手続きの中ですでに入力された情報をもう一度求める場合、自動で入れておくか、選べるようにすることを求める(例: 請求先住所の「配送先と同じ」チェック、エラーの後も入力済みの内容を消さない)。ブラウザの自動入力だけでは満たしたことにならず、サイト側で前の入力を引き継ぐ必要がある。パスワードの確認入力のようなセキュリティ上の理由、記憶ゲームのように再入力が本質的な場合、前の情報が無効になった場合は例外。
「Hostile Patterns in Error Messages」は、大半のケースでは、ユーザーがそのフィールドの入力を終えて次のフィールドへ移動するまでエラー表示を待つべきだとしている。入力中にエラーメッセージを表示するのは、頼んでもいない叱責のように感じられ、苛立たせる可能性があるため。「10 Design Guidelines for Reporting Errors in Forms」も同様に、理想的にはすべての検証をインラインで行い、ユーザーがフィールドの入力を終えた時点でエラーがあれば近くにインジケーターを表示すべきだとしつつ、パスワードのような複雑なフィールドでは、入力中に即座に検証するインライン表示(タイプ中に表示される)が有効だともしている。両記事を通じて一貫しているのは、「入力途中で急いで警告しない」という原則。
例外・許容ケース
数値の欄では、数字だけを受け付けて決まった形で表示する書式(number formatter)を使うとよいとしている。必須の入力がある場合は、入力が済むまで「次へ」などのボタンを使えないようにして、入力が必要なことを伝える。
検証をいつ行うか(入力中・欄を離れたとき・送信時)の決まりは、M3のテキストフィールドのページには書かれていない。
ARIA19のライブリージョンは、ページ読み込み時点でDOM内に空のコンテナとして存在している必要があり、後から動的に追加したコンテナには対応できない支援技術がある、という実装上の注意点がある。
必須項目が空欄のまま送信された場合のエラーは、送信を試みた後に表示するのが有用だとしている。技術的にリアルタイム検証ができない場合は、フォームやページが再読み込みされた際にエラーメッセージが分かりやすく見つけやすい場所にあるようにすべきだとしている。

根拠となる原則 ― POURのような適合区分ではなく、実際のユーザー体験調査(苛立ち・中断のしやすさ)に基づく実務的なタイミング指針。
ユースケース
  • 値は入力されたらすぐに確かめ、問題があればすぐに知らせる
  • ユーザー名・パスワードの作成は、次のフィールドに移る前に検証する
  • 数字専用フィールドなど値の種類が限定される場合は、不正な文字の入力時点で警告する
  • 書式のヒントは、エラーが起きる前からサポートテキストとして常に示しておく
  • 検証エラー時は同じ位置のテキストをエラーテキストに置き換える(改行によるレイアウト崩れを避ける)
  • パスワードのような複雑な入力は、検証を伴うテキストフィールドとして扱う
  • エラーメッセージ用のライブリージョンコンテナは、ページ読み込み時点でDOM内に空の状態で用意しておく
  • 検証タイミング自体に絶対的な基準はないため、他系列(特にNN groupの実務指針)を参考に決める
  • 送信が成功した場合も、成功したことを示す明示的なフィードバックを提供する(G199)
  • エラーで送り返しても、入力済みの内容を消さない(3.3.7)
  • 大半のフィールドは、ユーザーが入力を終えてフィールドを離れた時点(フォーカス離脱時)で検証する
  • パスワードの要件チェックリストなど、即時フィードバックがユーザーの助けになる場合のみ、入力中のリアルタイム検証を使う
  • 必須項目の未入力は、送信を試みた後にエラーとして示す

メモ

サイズ: 検証タイミング専用の数値基準はない。

ARIA19: role="alert"またはaria-live属性を持つライブリージョンに、JavaScriptでエラーメッセージを挿入することで、スクリーンリーダーに動的な変化を通知する技術。ライブリージョンのコンテナ自体はページ読み込み時点でDOM内に存在している必要がある。

G199: フォームやデータの送信が成功した際に、成功したことを明示的に伝えるフィードバック(「正常にログインしました」等)を提供する技術。

3.3.7 Redundant Entry・レベルA: 同じ手続きの中で、すでに入力・提供された情報をもう一度求める場合は、自動で入れておくか、選べるようにすることを求める基準(WCAG 2.2で追加)。
