コンポーネント / バッジSPEC No. 037

バッジ

アイコンやタブの角に重ねて、新着や未読の数を知らせる小さな印

コンポーネントイメージ(共通形状)
ドット(存在の有無)
12
数字(件数)

存在の有無だけを示すドット型と、具体的な件数を示す数字型の2種類が、Google(M3)・Apple・NN groupの定義に共通して見られる。

目的・役割
見るべきものがあることを、数字または点で控えめに知らせる
よく使われる場面
未読メールの件数、アプリアイコンの通知数、タブの新着の点
似たコンポーネント
内容そのものを伝えるならスナックバーやステータスメッセージ。バッジは数や有無だけを示す

まず押さえる要点

  1. 1
    件数に意味があるなら数字、あることだけ伝えるなら点
    AI解釈
  2. 2
    数が大きくなったら「999+」のようにまとめる
    AI解釈
  3. 3
    数字は最大4文字
    Google
  4. 4
    支援技術に伝わる名前に、件数を含める
    W3C 4.1.2。AI解釈

意見が分かれる点

同じ問いに対して、系列によって答えが違う点。図は概念図。

バッジは数字で出す?点(印だけ)で出す?
Google
2種類を使い分ける。小さいバッジ(点)は未読の知らせ、大きいバッジは件数(「+」を含め4文字まで、999+)
Apple
アプリアイコンのバッジは未読の通知の数(数字)。タブのバッジは数字か感嘆符
NN group
知らせの有無は多くは点、件数は多くは数字、と用語集で定義している
AI解釈: 件数そのものに意味があるとき(未読メール)は数字、新しいものがあることだけを伝えればよいとき(更新あり)は点、と分けると3系列で食い違わない。数字は大きくなりすぎたら「999+」のようにまとめる。

四系列デザインシステム比較

AI解釈 ― 総括

Communicationのページの中で、バッジは各系列の「専用ページの厚み」が最も薄いコンポーネントだ。Googleだけが「Badges」という独立したM3コンポーネントページを持ち、小(ドット)/大(数字・最大4文字)という2バリエーションを明確に定義している。一方でAppleは単独の「バッジ」ページを持たず、アプリアイコンの未読件数(Notificationsページ)とタブ上のバッジ(Tab Barsページ)という、性質の異なる2箇所の記述に分散している。

W3Cにはバッジ専用のARIAロールがそもそも存在しない。対応の一例は、装飾的なバッジ要素をaria-hiddenで隠し、件数などの意味を親のアイコンボタン側のaria-labelに含めるという、ARIA14の手法を当てはめた作り方だ(AI解釈)。4.1.2が求めるのは名前・役割・値をプログラムで取得できることで、この作り方を一律に求めているわけではない。

Nielsen Norman Groupの扱いも、独立記事ではなくUI Elements Glossaryの1項目としての簡潔な定義に留まる。Google・NN groupに共通するのは「ドットは存在の合図、数字は件数の定量化」という2区分の考え方だ。Appleはこの区分を書いておらず、タブのバッジは数字か感嘆符を使う(感嘆符は件数ではない)。W3Cは見た目の区分を定めていない。

総じてバッジは、4系列のどこにおいても「単体のコンポーネント」というより他コンポーネント(アイコン・タブ・通知)に付随する小さな装飾・情報要素として位置づけられており、この位置づけの軽さ自体が比較から見えてくる特徴だ。

推奨される使用シーン
  • アプリアイコン上で未読通知の件数を控えめに知らせたい時
  • タブバーの特定のタブに新着情報があることを示したい時
  • タブ・ナビゲーション項目に未読件数や新着の有無を示したい時
  • 存在の有無だけを伝えたい時は小サイズ(ドット)を使う
  • 具体的な件数を伝えたい時は大サイズ(数字・最大4文字)を使う
  • アイコンに重ねた件数バッジの意味を支援技術に伝えたい時
  • ドットのバッジで、色の違いだけで状態を分けてしまうのを避けたい時
  • アイコン上で通知の有無や件数を簡潔に示したい時

ドットは周りの色に対して3:1以上(1.4.11 非テキストのコントラスト)、数字はバッジの背景に対して4.5:1以上(1.4.3 コントラスト(最低限))。ドットの有無は色以外の手がかりなので、それだけで1.4.1(色の用途)の違反にはならない。ただし色の違いだけで状態を分けない(例: 赤と青のドットで意味を変えない)。ドットで新着を示すときも、支援技術には親要素の名前などで同じ意味を伝える。

基本方針
アプリアイコンのバッジは、未読の通知の数を示す小さな塗りの楕円で、数字を入れる。通知に対応すると消え、新しい通知が来ると再び出る。未読の通知の数だけに使い、天気・日時・株価・ゲームの得点など通知と関係のない数字には使わない。タブのバッジは、そのタブに注意すべき新しい情報があることを示す。
小さいバッジ(ドット)は存在を示すだけで文字を持たず、大きいバッジは数字やテキストで件数を示す。タブでは両方使え、ナビゲーションレールでは折りたたみ時はアイコンの右上、展開時はラベルの隣に置く。利用者が内容を確認したら、値を更新するか非表示にする。
専用のロールはない。関わるのは、達成基準4.1.2(名前(name)・役割(role)・値(value))と技法ARIA14(aria-labelで名前を付ける)。ARIA14は、文字のラベルを置けない要素にaria-labelで名前を付ける技法で、記号だけの閉じるボタンなどを例に挙げる(バッジ専用ではない)。バッジ付きのアイコンボタンに当てはめると、件数を親のボタンの名前に含め(例: aria-label="通知(4件)")、バッジはaria-hidden="true"で隠す(AI解釈)。名前と値をプログラムで取得できるようにすることが、4.1.2の求めに当たる。
UI Elements Glossaryは、バッジを、ショッピングカートやメッセージなどのアイコンに重ねて、通知の有無(多くはドット)や件数(多くは数字)を示す小さな要素と定義する。簡潔な定義に留まり、頻度・配色・乱用を避ける具体的な指針はない。
例外・許容ケース
利用者は設定でバッジを切れるため、重要な情報をバッジだけで伝えない。タブのバッジは重要な情報だけに使い、多用して意味を薄めない。
桁の多い件数は「+」付きで丸め、4文字以内に収める。
見えるラベルがあるなら、WCAG 2.5.3(Label in Name)により、aria-labelにもその文字列を含める(バッジ専用ではなく、ラベル全般の規定)。
用語の定義のみで、使ってよい場面・避ける場面の基準はない。
アクセシビリティ(WCAG基準)
記載なし
数値基準なし。バッジが伝える件数・状態は、バッジを付けたボタンなどの名前に含めて支援技術にも伝える(4.1.2 名前(name)・役割(role)・値(value))。色の違いだけで状態を伝えない(1.4.1 色の用途)。
堅牢(Robust)・知覚可能(Perceivable) ― 名前・役割・値をプログラムで判別できること(4.1.2)、色の違いだけで状態を分けないこと(1.4.1)、ドットや数字のコントラスト(1.4.11・1.4.3)。
根拠となる原則 ― 適合区分ではなく、用語集の定義。
ユースケース
  • 重要・新規の情報に限定して使い、多用を避ける
  • 対応済みの情報は速やかにバッジから取り除く
  • バッジだけで情報を伝えない(通知本体の補助に留める)
  • 存在のみを示す場合は小(ドット)、件数を示す場合は大(数字)を使い分ける
  • 件数は「+」付きで4文字以内に丸める
  • 確認された内容のバッジは速やかに更新・非表示にする
  • 装飾的なバッジ要素にはaria-hidden="true"を設定する
  • 件数などの意味は親要素(アイコンボタン等)のaria-labelに含める
  • 色の違いだけで状態を分けない。ドットで新着を示す場合も、親要素の名前などで同じ意味を支援技術に伝える
  • ドットは周りの色と3:1以上(1.4.11)、数字はバッジの背景と4.5:1以上(1.4.3)にする
  • 通知の有無を示す場合はドット、件数を示す場合は数字という使い分けの目安として参照する

小さいバッジと大きいバッジの使い分け(AI解釈): 数を出したくても、アイコンが小さく数字が読みにくい・場所が狭いときは、数字のない小さいバッジ(点)にし、件数は一覧の中など別の場所で示すのが実務的。Googleの公式の記述ではない(小さいバッジは未読の知らせ、大きいバッジは件数、という2種類はM3 Badgesにある)。

ARIA14 / aria-label: 見えるラベルを置けない要素に、aria-labelでアクセシブルネームを与える技法。バッジ付きのアイコンボタンで、装飾のバッジをaria-hidden="true"で隠し、件数を親のボタンのaria-labelに含める実装(例: aria-label="通知(4件)")は、これを当てはめた形(AI解釈)。
