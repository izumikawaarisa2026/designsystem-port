Foundation / アダプティブ・レスポンシブSPEC No. 052

アダプティブ/レスポンシブデザイン

画面の広さや向き、ウィンドウの大きさに合わせて、レイアウトを組み替える考え方

同じ内容を、画面の広さに合わせて組み替える(概念図)

狭い画面では下のナビゲーションと1列、広くなるにつれて横のナビゲーションと複数の区画(ペイン)に組み替える。内容と機能は同じまま、見せ方だけを変えるのが基本だ。ブレークポイントの値や余白は「レイアウト・スペーシング」ページを参照。

目的・役割
スマホからパソコンまで、どの大きさでも使いやすい配置にする
関わる場面
画面の回転、タブレットの分割表示、ブラウザの幅の変更、文字の拡大
関連するページ
レイアウト・スペーシング、ナビゲーションバー

まず押さえる要点

  1. 1
    内容と機能は同じに保つ
    広さが変わっても、見せ方だけを組み替える
    Apple・W3C
  2. 2

    サイズクラスで判断する
    Apple・Google
  3. 3
    ナビゲーションは広さで置き場所を変える

    Google・Apple
  4. 4
    広さが変わっても状態を保つ
    選択中の項目や開いている詳細を保つ

AI解釈 ― 総括

広さが変わっても内容と機能は同じに保ち、見せ方だけを組み替えるという考え方は、AppleとW3Cがはっきり示している。Appleは「広さによって機能を変えない」と明言し、W3Cは「320 CSS px相当まで狭めても情報と機能を失わない」ことを求めている。

組み替え方を最も具体的に決めているのはGoogleだ。Compactではナビゲーションバー、それより広ければナビゲーションレールに自動で切り替え(Jetpack ComposeのNavigationSuiteScaffoldの既定。M3の指針ではMediumはバーかレール)、リスト・詳細/フィード/補助ペインという3つのカノニカルレイアウトで、何列にするか(補助ペインはMediumで1:1、Expandedで7:3)まで示している。広さが変わったときに選択中の項目や開いている詳細を保つルールもある。

Appleは境界値を示さず、システムが決めるサイズクラス(compact/regular)で判断させる。広い画面ではタブバーをサイドバーに切り替え、スプリットビューで2〜3列にするなど、Googleと同じ方向の組み替えを勧めつつ、リサイズしてもプラットフォームらしいレイアウトのままにすることを重視している。

NN groupはWebのブレークポイントの目安として500px・1200px・1400pxを挙げ、実際には2〜3個で十分としている。切り替えでナビゲーションをハンバーガーに畳む・列を減らすときは、主な行動ボタンが埋もれないかの確認を求めている。実務では、Googleの型で組み替え方を決め、W3Cの320pxと縦横両方の向きで情報と機能が残るかを確かめるのが、4系列を合わせた結論だ。

Breakpoints in Responsive Design
位置づけ
端末の種類や向きではなく、システムが判定する「サイズクラス」(compact/regular)で見せ方を変える。機能は変えず、画面に見せる量とナビゲーションの形だけを変える
ウィンドウサイズクラスごとに、ナビゲーションのコンポーネントとペイン(画面の区画)の数を切り替える。よく使う形として「カノニカルレイアウト」(リスト・詳細/フィード/補助ペイン)が3種類ある
どの広さで何に切り替えるかは定めず、「狭くしても・向きを変えても、情報と機能が失われないこと」を求める
Webのレスポンシブデザインで、ブレークポイント(レイアウトを切り替える幅)を4段階で考える(適合基準ではない)
切り替えの基準
広さの区分は横・縦それぞれcompact/regularの2つで、境界値は公開されていない。対応する変化として、画面サイズ、向きと縦横比、Dynamic Islandなどのシステムの機能、外部ディスプレイ・画面の拡大・iPadとMacのウィンドウのリサイズ、文字サイズの変更、地域の設定(右から左の表記・日付や数字の書式・文字の長さ)を挙げる。
ナビゲーションは、幅か高さがCompact(またはテーブルトップの姿勢)ならナビゲーションバー、それ以外はナビゲーションレールに自動で切り替わる(NavigationSuiteScaffoldの既定)。リスト・詳細は、Expanded幅でリストと詳細を並べ、Medium・Compact幅ではどちらか一方だけを表示する。補助ペインは、Medium幅で主と補助を1:1、Expanded幅で7:3に分け、Compact幅では下に置くかボトムシートに入れる。
1.4.10(レベルAA): 縦にスクロールする内容は幅320 CSSピクセル相当、横にスクロールする内容は高さ256 CSSピクセル相当で、情報や機能を失わず、縦横2方向のスクロールなしで表示できること。320pxは、幅1280pxの画面を400%に拡大した状態にあたる。1.3.4(レベルAA): 表示と操作を縦向き・横向きのどちらか一方に限定しないこと。
標準はないとしたうえで、よく使う目安としてExtra-small 500pxまで(スマートフォン・4列のグリッド)、Small 500〜1200px(タブレット・8列)、Medium 1200〜1400px(ノートパソコン・12列)、Large 1400px以上(外部モニター・12列)を挙げる。実際は2〜3個のブレークポイントに対応するのが一般的。
切り替えるもの・保つもの
広い画面では、タブバーをサイドバーに切り替えたり、オーバーフローメニューにまとめていた機能を表に出したりしてよい。iPadOSでは、サイドバーに切り替えるボタン付きのタブバーを出せる。スプリットビューはiPadOSで2列(メールのように)か3列(Keynoteのように)。iPhoneの縦向きのようなcompactでは、スプリットビューを使わない。
広さが変わっても状態を保つ。リストと詳細を並べていた画面が狭くなったら、詳細を残してリストを隠す。詳細だけを表示していた画面が広くなったら、リストも並べ、詳細に表示中の項目をリストで選択中として示す。リストだけのときに広くなったら、空の詳細ペインを並べる。
見た目の切り替え方は自由。求めるのは結果で、拡大して幅が狭くなったら1列に組み替わり、横スクロールせずに読めること。向きは、利用者が好む向きで表示できるようにする。
典型的な変化は、ナビゲーションを変える(左のナビゲーションをハンバーガーメニューに畳む)、列を畳む(右の列を本文に入れる・別の場所に移す)、1行に見える要素の数を変える、の3つ。例として、広い画面で一覧と地図を並べ、タブレットでは地図をボタンの奥に隠すサイトを紹介する。
基本方針
回転・ウィンドウのリサイズ・ディスプレイの追加・別の端末への切り替えのどれでも、体験が変わらず慣れたものに感じられるようにする。そのためにセーフエリア・マージン・レイアウトガイドを守る。サイズクラスの組み合わせはすべて起こりうるため、縦横どちらの向きでも全部を検討し、最大と最小のレイアウトから確かめると効率的。
カノニカルレイアウトは、スマートフォンからタブレット・折りたたみ端末・ChromeOSまで、多くの画面で実績のある汎用の形で、Material Designの指針から作った。広い画面でレールにするのは、タブレットを両手で持ったとき左右の端に手が届きやすいため。
大きな文字が必要な人には、長い行を読むために横にスクロールし続けるのが難しいため。向きは、車いすのアームなどに端末を固定して使う人は回転させられないため。
ブレークポイントの値は、利用者の端末を分析して、開発チームと一緒に決める。各サイズで、知るべきことがすぐ手に入るか、列を縦に積んだとき重要な操作(右の列にあった主な行動ボタンなど)が見つけにくくならないかを確かめる。
例外・許容ケース
横向き専用のゲームのように向きを固定するアプリでも、ウィンドウや端末の大きさの違いには対応する。背景の画像は、縦横比を変えずに拡大して画面を埋める。macOSのスプリットビューは縦・横・両方に分割でき、ペインに最小・最大の大きさを決めたり、作業に集中するためにペインを隠せるようにしたりする。
補助ペインは、主の内容と組み合わせて初めて意味を持つもの(文書へのコメント、動画の関連動画、編集ツールのパレットなど)に使い、単独でも意味のある詳細(商品の説明など)はリスト・詳細を使う。フィードは、1列のスクロールから複数列のグリッドまで、画面の広さに合わせて列の数を変える。
1.4.10は、使い方や意味のために2次元の配置が必要な部分(理解に必要な図や地図、動画、ゲーム、プレゼンテーション、データ表、操作中に表示し続ける必要があるツールバー)を例外とする。1.3.4は、小切手、ピアノのアプリ、プロジェクターやテレビ向けのスライド、VRのように、特定の向きが欠かせない場合を例外とする。
ブレークポイントを増やすほど細かく対応できるが、手間が増えるため、実際は2〜3個に絞ることが多い。重要な操作が埋もれるなら、前の内容をアコーディオンに畳むなど、通常の積み方の例外を作ってよい。
アクセシビリティ(WCAG基準)
知覚可能(Perceivable) ― 文字を大きくしたら、横並びを縦に積み直し、行の高さを伸ばして文字の切れや重なりを防ぐ。WCAG 1.4.10(リフロー)・1.4.4(テキストのサイズ変更)と同じ目的。
―(アダプティブ専用のアクセシビリティ基準はない)。狭い画面で1ペインに切り替える設計は、WCAG 1.4.10(リフロー)の「狭い幅でも2方向にスクロールせずに読めること」を満たしやすくする。
知覚可能(Perceivable) ― 1.4.10・1.3.4はどちらも「知覚可能」。拡大して使う弱視の人や、端末を固定して使う人が、同じ情報と操作にたどり着けるようにする。
根拠となる原則 ― 適合区分ではなく、Webのレイアウト設計の実務にもとづく指針。
ユースケース
  • レイアウトは端末の種類や向きではなく、サイズクラスで切り替える
  • 広い画面ではタブバーをサイドバーにし、隠していた機能を表に出す(機能そのものは変えない)
  • 最大と最小のレイアウト、最大の文字サイズで、切れや重なりがないか確かめる
  • Compactではナビゲーションバー、それより広い画面ではナビゲーションレールにする
  • 一覧と詳細があるアプリ(メッセージ・連絡先など)は、Expanded幅で2ペインを並べる
  • 広さが変わっても、選択中の項目や開いている詳細を失わない
  • 幅320pxで、横スクロールが出ないか、情報や機能が消えていないか確かめる
  • 縦向き・横向きのどちらでも使えるようにする(向きを固定しない)
  • データ表・地図など2次元が必要な部分だけ、横スクロールを許す
  • ブレークポイントは利用者の端末の分析から決め、名前(S/M/Lなど)を付けて共有する
  • 狭い画面では、左のナビゲーションをハンバーガーに畳み、本文に集中させる
  • 列を縦に積んだとき、主な行動ボタンが下に埋もれないか確かめる

アダプティブとレスポンシブの違い

レスポンシブは1つのレイアウトを画面に合わせて伸び縮みさせること。アダプティブは端末ごとに体験を作り分けること。色・文字・形だけでなく、構造やコンポーネント、レイアウト全体を変える

画面の骨組み ― バー・レール・ペイン

上下のバー(アプリバー・ナビゲーションバー)、その内側や左右のレール(ツールバー・FAB・ナビゲーションレール)、内容を入れるペインの順に組み立てる。画面の上下端のシステムの領域には主な内容を置かない
