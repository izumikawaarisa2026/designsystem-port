アイコン(サイズ・スタイル)

アイコンの大きさ・線の太さなどのスタイルと、意味の伝え方の決まり

サイズの目安(概念図)
16pt/dp
24pt/dp
32pt/dp

同じ形のアイコンでも、系列・文脈によって最適なサイズ・太さ・スタイルは異なる。実寸の基準は各系列の欄を参照。

アイコンのスタイルの考え方 ― 形・線の太さ・色

アイコンの描き方を決めているのはAppleとGoogleだ。どちらも隣の文字と線の太さ・大きさをそろえることを求めている。W3Cは形や色を定めず、意味を伝えるアイコンに背景との3:1のコントラスト(1.4.11)と代わりの文字(1.1.1)を求める。NN groupも描き方は定めず、文字のラベルを添えることを勧めている。

Apple(SF Symbols・Icons)Google(Material Symbols)
考え方単純で、すぐに分かる形にする。身近な比喩を使い、アプリの中のアイコンは大きさ・細かさ・線の太さ・視点をそろえる単純・現代的・親しみやすく、ときに遊び心がある形。細く頼りない線ではなく、くっきり太めに描く。1つのセットの中でスタイルを混ぜない
形非対称の形は、図形の中心ではなく見た目の中心に合わせる(余白を含めた画像にする)。状態は塗り(fill)・斜線(slash)・囲み(enclosed)の形の違いで表す24dpのグリッドの中、20dpの範囲に描く。基準の形(正方形18dp・円20dp・縦長20×16dp・横長16×20dp)で大きさをそろえる。角の丸みは2dp。スタイルはアウトライン・ラウンド・シャープの3種類
線の太さウルトラライトからブラックまでの9段階。San Franciscoの文字の太さと対応し、隣の文字と同じ太さにするのが基本標準は2dp(太さ400)。100〜700で変えられるが、24dpでは200より細くしない。光学サイズ(20〜48dp)で、大きさが変わっても線の太さが自然に見えるよう自動で調整する
色形は黒と透明で作り、色はシステムが付ける。色の付け方は4つのモード(単色・階層・パレット・マルチカラー)。量の変化には可変カラーを使い、奥行きの表現には使わない塗り(Fill 0〜1)で未選択と選択を切り替える(例: ナビゲーションバー)。暗い背景の明るいアイコンは太く見えやすいため、グレード-25で細く補正する。色の意味は文化で違う(赤と緑の警告など)

出典: HIG「Icons」「SF Symbols」、Material Design 3「Designing icons」「Applying icons」。

Apple・Googleのサイズと余白(スペーシング)の比較

アイコン本体の大きさ、押せる範囲、コンポーネントの大きさの段階、アイコンの周りの余白を比べる。Googleはアイコンボタンの段階ごとに余白まで数値で決めているのに対し、Appleはアイコン自体の大きさを文字に合わせ、押せる範囲(44pt)を中心に定めている。

pt数の段階はなし。SF Symbolsは隣の文字のサイズに合わせて表示され、small/medium(既定)/largeの3スケールで文字との比率を変える。

アイコンの周りの余白
数値の指定はなし。非対称なアイコンは、見た目の中心が合うよう余白を含めた画像にして中心をそろえる(光学的な中心合わせ)。macOSの書類アイコンは、画像を枠の約80%に収め、約10%の余白を取る。
容器の端からアイコンまでの余白が段階ごとに決まっている。標準幅でXS 6 / S 8 / M 16 / L 32 / XL 48dp。さらに狭い(Narrow)・広い(Wide)の3種類の幅がある(例: Sは4 / 8 / 14dp)。
並べるときの間隔
visionOSでは、ボタンの中心どうしを60pt以上離す。60pt以上のボタンには、ホバー効果が重ならないよう周りに4ptの余白を取る。
アイコンボタン自体の間隔の数値は記載なし(押せる範囲48dpを確保すれば重ならない)。

四系列デザインシステム比較

AI解釈 ― 総括

Apple・Googleはどちらも可変的なアイコン体系(SF Symbols / Material Symbols)を持ち、単一のスタイルではなく複数のウェイト・スタイル・サイズを1つのフォント技術で連続的に切り替えられるようにしている。Appleは隣接するテキストとのウェイト一致を重視し、Googleはoptical size軸によるストローク幅の自動最適化を重視するなど、同じ「可変フォント」的アプローチでも力点が異なる。

W3Cは、アイコンそのものの見た目ではなく「意味がちゃんと伝わるか」を3段階(代替テキスト・プログラム的な名前・コントラスト比)で規定している。特に4.1.2は、アイコンのみのボタンに視覚的なラベルがなくても、支援技術に伝わる名前さえあれば基準を満たせるとしており、Apple・Googleのようなビジュアル面の柔軟性とは別の軸の要求だ。

Nielsen Norman Groupの指摘は、Apple・Googleが提供する洗練されたアイコン体系があっても「アイコン単体の意味は標準化されていないことが多い」という現実を突いている。5秒ルールや再認・記憶テストといった実務的な検証手法は、W3Cの「プログラム的な名前」という技術要件だけでは解決しない、視覚的に見ただけで意味が伝わるかという別の問題を扱っている。

サイズ
スケールは3段階(small / medium(既定) / large)で、San Franciscoのキャップハイト(大文字の高さ)が基準。シンボルは隣の文字のポイントサイズに合わせて表示し、スケールで文字に対する強弱を調整する。スケールごとのptの数値はない。
オプティカルサイズ(opsz)軸は20〜48dp。表示サイズを変えても同じ見た目になるよう、線の太さが自動で調整される。Google Fontsから読み込んだときの既定値はopsz 48・weight 400・grade 0・fill 0。
アイコン専用の数値基準はない。アイコンを押せるコンポーネントとして使う場合は、2.5.8(AA)の24×24 CSS px以上(例外あり。詳しくはボタンのページ)。より高い水準の2.5.5(AAA)では44×44 CSS px以上(例外あり)。
数値基準なし。押すのに十分な大きさを持たせつつ場所を節約できる点を、アイコンの利点に挙げる。
色
4つのレンダリングモードで色の付け方が変わる。モノクローム(単色、最も中立的)・階層的(1つの色相の濃淡で奥行きを表す)・パレット(2色以上のコントラストで要素を強調)・マルチカラー(シンボル自体が複数の色を持つ)。
数値基準なし。weight軸・grade軸で、太さ・濃さの印象を調整できる。

基本方針
ウルトラライトからブラックまでの9段階のウェイトが、隣の文字のSan Franciscoのウェイトと対応し、シンボルと文字が調和する。スケール(small/medium(既定)/large)はキャップハイトが基準で、同じポイントサイズの文字とのウェイトの対応を崩さずに強弱を調整できる。選択状態はfill、使えない状態はslashといった種類で表せる。
Material Symbolsは、Outlined(密なUIに向く軽く整ったスタイル)・Rounded(角丸で、太めの文字やロゴと調和)・Sharp(直線的で、小さくても見やすい)の3スタイル。別の「Filled」フォントはなく、各スタイルのfill軸で塗りを表す。fill・weight・grade・optical sizeの4軸で、1つのフォントファイルで幅広い見た目を表せる。
1.1.1は、意味を伝える文字以外のコンテンツに、同じ情報を別の形(視覚・聴覚・触覚のどれでも認識できる形)で伝える代替テキストを求める。短い代替で伝えきれればそれでよいが、複雑な図表などでは長い説明が要る。アイコンが操作要素なら、見た目の説明ではなく「その操作が何をするか」を説明する名前が要る。4.1.2は、すべてのUIコンポーネントの名前・役割をプログラムで判別できるようにすること(名前は見えなくてもよいが、支援技術にはいつも伝わる必要がある)。1.4.11は、UIコンポーネントを見分ける見た目と理解に必要な図の一部に3:1以上を求める。3.2.4(レベルAA)は、ページをまたいで出てくる同じ働きのコンポーネントを一貫して識別できること。全ページ共通の検索・アカウントなどのアイコンボタンには、どのページでも同じ意味が伝わる名前(代替テキスト)を付ける。
アイコンは押しやすく、場所を節約でき、見慣れたものなら素早く分かり、言語を越えて通じ、見た目を一貫させる。一方「アイコンの理解は過去の経験にもとづく」ため、多くのアイコンは意味が標準化されておらず曖昧になる。例は、ハンバーガーメニュー(一覧を表す場合もある)やハート(お気に入り・保存・評価など用途がまちまち)。そのため、ほぼすべてのアイコンに意味を補う文字のラベルが要り、ホバーなどの操作なしでいつも見せる。標準的なアイコンでも、見た目を少し変えたならラベルを付けるほうが安全。
例外・許容ケース
どのモードを使うかの決まりはない。サイズや背景とのコントラストで細部の見えやすさが変わるため、使う場所ごとに見え方を確かめる。自動設定でシンボルごとの推奨モードも使える。可変カラー(Variable color)は量や強さの変化を表すもので、奥行きには使わない(奥行きは階層的モード)。
gradeは、暗い背景の明るいアイコンのにじみを抑えるなら低い値(例: -25)、強調したいなら高い値(例: 200)にする。文字のフォントがgrade軸を持つなら、文字とアイコンのgradeをそろえると調和する。
1.4.11は、無効(非アクティブ)なコンポーネントにはかからない。ロゴ・旗・写真など、見た目そのものが情報として欠かせない場合も例外。1.1.1も、装飾だけで情報を持たない画像は対象外。
ふさわしいアイコンを思いつくのに5秒以上かかるなら、アイコンで意味を伝えるのは難しい(5秒ルール)。デザインはシンプルで図式的にし、小さくすると潰れる細部は避ける。競合やプラットフォームの慣習を先に調べる(利用者の期待は既存のパターンに従いやすい)。
アクセシビリティ(WCAG基準)
知覚可能(Perceivable) ― 専用の数値基準はないが、どのモードでもシステムカラーを使えば、アクセシビリティの設定やダークモードに自動で追従する。アイコン単体の意味の伝え方はW3C(1.1.1/4.1.2)を参照。
操作可能(Operable)・知覚可能(Perceivable) ― アイコン単体の意味の伝え方はW3C(1.1.1/4.1.2)を参照。Material Symbols専用のアクセシビリティの数値基準はない。
知覚可能(Perceivable)・堅牢(Robust) ― 1.1.1(文字の代替)と1.4.11(見分けやすさ)は「知覚可能」、4.1.2(支援技術に伝える)は「堅牢」で、それぞれ別の失敗を防ぐ。3.2.4は「理解可能(Understandable)」の予測可能(3.2)、2.5.3は「操作可能(Operable)」の入力方法(2.5)。
根拠となる原則 ― 適合区分ではなく、認識しやすさ(recognizability)・覚えやすさ(memorability)のユーザビリティ調査にもとづく指針。
ユースケース
  • 隣の文字のウェイトに合わせてシンボルのウェイトを選ぶ
  • 文脈に応じてスケール(small/medium/large)を使い分ける
  • 中立に見せたいならモノクローム、強調したいならパレット/マルチカラーを検討する
  • 密なUIにはOutlined、丸みのあるブランドにはRounded、直線的で小さいスケールにはSharpを選ぶ
  • 表示サイズに合わせてoptical size軸を調整し、線の太さを整える
  • 塗りの状態(選択中など)はfill軸で表す(別のスタイルに切り替えない)
  • 意味を持つアイコンには代替テキストを用意する(装飾目的のみの場合は不要)
  • アイコンだけのボタン・リンクには、aria-label などで名前を必ず付ける
  • UIコンポーネントとして働くアイコン・境界線は、隣の色と3:1以上にする(無効な状態・ロゴなどの例外を除く)
  • 全ページ共通のアイコンボタンには、どのページでも同じ意味が伝わる名前を付ける(3.2.4)
  • 見えるラベルを付けたアイコンは、支援技術向けの名前(aria-labelなど)にも同じ言葉を含める(2.5.3)。食い違うと、音声入力でラベルの言葉を言っても反応しない
  • 意味が標準化されていないアイコンには、いつも見える文字のラベルを添える(ホバーのときだけ出すのは避ける)
  • 出す前に再認テスト(何を意味するか)と記憶テスト(数週間後も覚えているか)を行う
  • シンプルで図式的にし、小さくしても潰れないようにする

メモ

fill軸: 塗りの有無を切り替える軸。0が既定(輪郭のみ)、1が完全な塗りで、1つのアイコンで未選択/選択の両方を表せる。状態の切り替えのアニメーションにも使う。別の「Filledフォント」ではなく、Outlined/Rounded/Sharpそれぞれの可変フォントの1軸。

optical size(opsz)軸: 20〜48dpでアイコンの表示サイズを指定する軸。値に合わせて線の太さが自動で調整され、サイズを変えても同じ見た目に保たれる。

weight軸・grade軸: weightは線の太さで、thin(100)〜bold(700)の範囲。gradeはweightより細かい太さの調整で、アイコンの大きさへの影響が小さい。暗い背景の明るいアイコンのにじみを抑えるには低いgrade(例: -25)、強調には高いgrade(例: 200)を使う。

メモ

1.1.1 Non-text Content(レベルA): 意味を伝える文字以外のコンテンツ(アイコン・画像など)に、同じ目的を果たす文字の代替を用意すること。アイコンが操作要素(ボタンなど)なら、見た目の説明ではなく「その操作の目的を説明する名前」が要る。

4.1.2 Name, Role, Value(レベルA): すべてのUIコンポーネントの名前と役割を、プログラムで判別できるようにすること。名前は見えなくてもよいが、支援技術が取得・通知できる形で必要。アイコンだけのボタンに aria-label などで名前を与えるのが代表的な実装。

1.4.11 Non-text Contrast(レベルAA): UIコンポーネントを見分けるのに必要な見た目と、理解に必要な図の一部に、隣の色と3:1以上を求める。2.999:1のようなわずかな未達も不合格になる厳密な基準。

3.2.4 Consistent Identification・レベルAA: ページをまたいで出てくる同じ働きのコンポーネントを、一貫して識別できること。文言が完全に同じでなくてよい。

2.5.3 Label in Name(レベルA): 見えるラベル(文字)があるコンポーネントは、支援技術向けの名前にもその言葉を含めること。食い違うと、音声入力でラベルの言葉を言っても反応しない。
