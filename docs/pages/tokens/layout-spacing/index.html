レイアウト・スペーシング(余白・グリッド)

余白の刻み、画面の幅に応じたレイアウトの切り替え、要素のまとめ方の決まり

余白が「まとまり」を作る(近接の原則)

同じ12個の四角でも、間隔を変えるだけで1つのまとまりにも2つのグループにも見える。余白は見た目を整えるだけでなく、要素どうしの関係を伝える情報だ。

目的・役割
余白をそろえて関係のある要素をまとめ、画面の構造を分かりやすくする
関わる場面
コンポーネントどうしの間隔、画面の端の余白、列(グリッド)の数
関連するページ
レスポンシブデザイン

まず押さえる要点

  1. 1
    余白でまとまりを作る
    関係のある要素は近づけ、別のグループは間を広げる
    NN group
  2. 2
    狭めても読めるようにする
    幅320 CSS pxまで狭めても内容を読める(データの表・地図などは例外)
    W3C 1.4.10
  3. 3
    切り替える幅の目安
    600・840・1200・1600dp(端末ではなく使える広さで切り替える。詳しくは「レスポンシブデザイン」)
    Google。Appleは境界値を示さない

四系列比較図 ― レイアウトを切り替える幅の境界(dp / CSS px)

Googleの帯はウィンドウサイズクラス(幅)の区分だ。W3Cの320pxはレイアウトの境界ではなく、この幅でも内容を読めることを求める値だ。単位(dp・pt・CSS px)は厳密には異なるが、いずれも画面の密度に依存しない論理的な単位だ。

余白とレイアウトを図で見る

Google ― 画面の幅ごとの余白とペイン(dp)

画面の端の余白はCompactで16dp、それより広い幅で24dp。ペインとペインの間(スペーサー)は24dp。幅の決まったペインはExpandedで360dp、Large以上で412dp。図は幅の比率を合わせた概念図だ(出典: M3「Breakpoints」「Panes」)。

Apple ― 分割ビュー(1つの画面を2〜3列に分ける)

分割ビューは、画面を縦に2〜3列に分け、左の列で選んだ項目の中身を右の列に出す見せ方。メールアプリなら、フォルダ→メールの一覧→本文を1画面に並べ、画面を移らずに階層をたどれる。広い画面(iPadOS・macOS)向けで、狭い幅(compact)では1列ずつ表示する。余白の数値は示されず、システムのマージンとセーフエリアに合わせる。

四系列デザインシステム比較

AI解釈 ― 総括

AppleとGoogleは、端末の種類ではなく、使える画面の広さで切り替える点が同じ。違いは数値の公開で、Googleは境界(600・840・1200・1600dp)と余白(端16/24dp・ペインの間24dp)を示し、Appleはシステムのマージンに任せる。

W3Cは余白を指定せず、幅320pxでも読めること(1.4.10)を求める。NN groupの近接の原則とW3Cの1.3.1を合わせると、余白で作ったまとまりは、構造でも伝えておく(AI解釈)。

位置づけ
余白の刻みは定めず、システムのマージンとセーフエリアに従う。画面の広さはサイズクラス(compact/regular)で判断する
使える幅を5段階のウィンドウサイズクラスに分け、区分ごとにレイアウト(1ペイン/2ペインなど)を切り替える
余白やグリッドの値は定めず、狭い幅でも読めること・押す対象の間隔・まとまりを構造でも伝えることを求める
余白は「何と何が関係しているか」を伝える手段、という近接の原則にもとづく
余白・グリッドの数値
iOS/iPadOSは数値なし(システムのマージンに任せる)。watchOSは1行のボタンをアイコン3つ・文字2つまで。
画面端16dp(Compact)・24dp(それ以外)、ペインの間24dp。幅の決まったペインはExpanded 360dp・Large以上412dp(上の図)。
幅320 CSS pxでも2方向のスクロールなしで読めること(1.4.10・AA。1280pxを400%に拡大した幅)。データの表・地図など、2方向の配置が意味に必要な内容は例外。押す対象は24×24 CSS px以上か、中心どうしを24px以上離す(2.5.8・AA、例外あり)。
原則としての言及。例: 12項目のフォームは、4項目×3グループに分けると取り組みやすく見える。
画面幅による切り替え
サイズクラスは横・縦それぞれcompactかregularで、システムが決める(境界値の記載なし)。端末の種類や向きではなくサイズクラスで切り替え、使える機能は変えない。
幅の境界は600・840・1200・1600dp(上の比較図)。高さがCompact(480dp未満)なら、幅がMediumでも2ペインは避ける。
幅ごとの決まりはない
記載なし
構造・グループ化
関連する項目は、余白・容器の形・区切り線でまとめる。
線・区切り線・影で囲む明示的なまとめ方と、近さと空きで示す暗黙のまとめ方がある。
1.3.1(A): 余白でまとめたグループは、構造でも支援技術に伝える(余白だけでは読み上げで伝わらない)。
近接は色や形の似ていることより優先されることがある。見出しは自分の節の本文に近く置く。
基本方針
重要なものを上・行の始まり側に置き、揃えと字下げで階層を表す。文字が大きくなったら、横並びを縦に積み直して切れや重なりを防ぐ。
サイズクラスはアプリが実際に使えるウィンドウの大きさで決まり、分割画面や折りたたみで変わる。「タブレットかどうか」の判定には使わない。
余白の大きさや列数は指定しない。結果としての使いやすさ(狭い幅で組み替わる・近づけすぎない・構造でも伝える)を求める。
関連する要素は近くに、関係のない要素は離して置く。関連する操作が離れていると、作業に集中している人は見落とす。
例外・許容ケース
向きを固定するアプリでも、端末やウィンドウの大きさの違いには対応する。
Large・Extra-largeは、デスクトップや外部ディスプレイのために後から加えた区分。
1.4.10は、地図・図・動画・ゲーム・データ表など2次元の配置が欠かせない部分を除外。2.5.8の例外は5つ(詳しくはボタンのページ)。
狭い画面で別のグループが同じグループに見えるなら、配置そのものを変える。
アクセシビリティ(WCAG基準)
知覚可能 ― 文字の拡大で組み替えるのは、WCAG 1.4.10・1.4.4と同じ目的。
知覚可能 ― 狭い幅で1ペインに切り替えると、WCAG 1.4.10(リフロー)を満たしやすい。
知覚可能(1.4.10・1.3.1)・操作可能(2.5.8)。
根拠となる原則 ― 適合区分ではなく、知覚の原則とユーザーテストにもとづく。
ユースケース
  • 余白は独自の数値ではなく、システムのマージンを使う
  • 文字を最大にしたら横並びを縦積みに変える
  • Medium幅以上では2ペイン(一覧+詳細)を検討する
  • 幅320pxで横スクロールが出ないか確かめる
  • 余白でまとめたグループは、見出しやグループの構造でも伝える
  • ラベルと入力欄の間は狭く、次のラベルとの間は広く
  • 関連する操作(戻る/次へ)はまとめる

1.4.10 Reflow・レベルAA: 幅320 CSS px相当まで狭めても、縦横両方向のスクロールなしで読めること。地図・図表・データ表など2次元の配置が要る部分は例外。

2.5.8 Target Size (Minimum)・レベルAA: 押す対象を24×24 CSS px以上にするか、小さいなら周りに十分な間隔を取ること。文中のリンクなどは例外。

1.3.1 Info and Relationships・レベルA: 見た目で表している構造や関係を、見出し・リスト・グループなどのマークアップでも表すこと。
